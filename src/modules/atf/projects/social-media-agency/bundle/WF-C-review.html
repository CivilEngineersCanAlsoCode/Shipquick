Content Review — Overview

Goal: Let user review upcoming scheduled posts and make last-minute changes before n8n auto-publishes them.

System: BMAD workflow — interactive. This is the quality gate between formatting and publishing.

Agent: Pixel (flex-crafter)

Steps

  1. C.1 — Fetch Scheduled — Fetch all posts with status Previewed via sma-fetch-post, sort by date, present summary
  2. C.2 — Preview & Decide — Show formatted preview in code block, user decides: approve / edit / reschedule / drop / send back
  3. C.3 — Apply Minor Edits — If user chose edit: apply changes, re-validate formatting, re-preview, loop until approved
  4. C.4 — Finalize Review — Summary of all decisions, retry any failed saves, offer next workflow actions

Webhooks

WebhookMethodSteps
sma-fetch-postPOSTC.1
sma-update-postPOSTC.2, C.3, C.4

Inputs

  • MongoDB linkedin_posts collection (status: Previewed)

Outputs

  • Approved posts → status Ready_ToPublish (n8n auto-publishes via D-ContentPublishing)
  • Edited posts → updated formatted_content + status Ready_ToPublish
  • Rescheduled posts → new scheduled_date (conflict-checked, 1 post/day max)
  • Dropped posts → status Cancelled
  • Sent-back posts → status Scheduled_NoDraft (returns to B-ContentDrafting)

Agent Instructions

Overview

This workflow is the quality gate between formatting and publishing. The agent fetches all posts with status Previewed, presents each one to the user for review, and applies the user's decision (approve, edit, reschedule, or drop). Approved posts are updated to Ready_ToPublish in MongoDB, making them eligible for auto-publication by D-ContentPublishing.

Agents Involved

  • Pixel (flex-crafter): Presents posts for review, applies user decisions, updates MongoDB.

Phase 1: Fetch Posts (Step C.1)

  1. Fetch Scheduled Posts: POST to sma-fetch-post with { "status": "Previewed" } to retrieve all formatted and previewed posts.
  2. Sort by scheduled_date ascending (soonest first — most urgent reviews first).
  3. If no posts found, inform user: "Koi previewed post nahi hai abhi. Pehle F-ContentFormatting run karo."
  4. Display summary with count and table of topics, channels, and dates.
  5. Ask: "Ek ek karke review karein? (haan/nahi)"

Phase 2: Review Each Post (Step C.2)

  1. Preview & Decide: For each post (chronological order):
    • Display full content in a code block (as it will appear on LinkedIn)
    • Show metadata: topic, content pillar, scheduled date/time, channel, frameworks used
    • User decides: Approve, Edit, Reschedule, Drop
  2. Apply Decision:
    • Approve: POST to sma-update-post with { "status": "Ready_ToPublish" }
    • Edit: Apply changes to draft_content, POST updated content. Re-present for approval. Suggest send-back if major edit needed.
    • Reschedule: POST with new scheduled_date. Verify no date conflicts.
    • Drop: POST with { "status": "Cancelled" }.
  3. Next Post: Move to next in queue. Repeat until all reviewed.

Phase 3: Summary (after all posts)

  1. Show Summary: "{approved_count} approved, {edited_count} edited, {rescheduled_count} rescheduled, {dropped_count} dropped"
  2. Offer Next Actions: Draft new content (B), Run ideation (A), or exit.

Key Constraints

  • This is the LAST human checkpoint before auto-publication — be thorough
  • Posts must have status Previewed to enter this workflow (already formatted)
  • Approved posts will be auto-published by n8n — no retry, one shot only
  • MongoDB is source of truth — all updates via sma-update-post
  • Agent has ZERO direct DB/API access — all via n8n webhooks
  • If a post needs major rework, send back to B-ContentDrafting (status: Scheduled_NoDraft)
  • All user communication in Hinglish

Success Criteria

  • Every previewed post has a user decision (no posts left unreviewed)
  • Approved posts have status Ready_ToPublish in MongoDB
  • Edited posts have updated draft_content saved
  • Rescheduled posts have new dates with no conflicts
  • Dropped posts have status Cancelled
  • User saw full content preview before each decision
  • Summary presented at end of review session

Dependencies

MANDATORY EXECUTION RULES:

  5. [PROCEED] → C.1 (Fetch Scheduled Posts)

Step 01b — Resume If Interrupted

Purpose

Recover workflow state after an interruption and resume from the last reviewed post.

Dependencies

  • Requires: Previous session state (partial execution of C.1–C.2)

Execution Protocols

  1. [CHECK] Determine last completed step by checking available state:
    • posts_to_review[] populated? → C.1 completed
    • decisions{} has entries? → C.2 partially completed
    • All posts have decisions? → C.2 completed (workflow done)
  2. [RECOVER] Based on last completed step:
    • If interrupted at C.1: Re-fetch posts (idempotent read). Posts with changed status won't appear — this is correct behavior.
    • If interrupted at C.2: Re-fetch remaining Previewed posts. Previously decided posts already have their new status. Resume from first remaining Previewed post.
  3. [INFORM] Tell the user: "Pichli session resume kar raha hoon — {decided_count} posts already reviewed, {remaining_count} baaki hain."
  4. [PROCEED] Jump to C.2 with remaining posts.

Rules

  • NEVER re-review a post that already has status Ready_ToPublish or Cancelled
  • The re-fetch naturally filters out already-decided posts (they're no longer Previewed)
  • If no Previewed posts remain, workflow is complete — show summary
  • If state is completely lost, restart from C.1 (fetch is idempotent, already-decided posts excluded)

Step C.2 — Preview Post & Get User Decision

Agent: Pixel (flex-crafter)
Trigger: Automatically after C.1 for each post in posts_to_review[].

What You Do

For each post, display the full formatted preview exactly as it will appear on LinkedIn, show all metadata, and ask the user to make a decision: approve, edit, reschedule, drop, or send back.

Display Format

  1. Metadata Header: Post number, topic, content pillar, scheduled date, channel, format, hook, narrative, CTA, tone.
  2. Content Preview: formatted_content inside a code block — exact formatting as LinkedIn will render it.
  3. Quick Stats: Characters (/ 1600 max), Emojis (/ 3 max), Hashtags count.
  4. Decision Prompt:
    1. Approve — As-is publish on scheduled date
    2. Edit — Minor changes (typo, word change, line tweak)
    3. Reschedule — Date/time change
    4. Drop — Cancel post, do not publish
    5. Send Back — Major rework needed, back to drafting

Decision 1: Approve

POST sma-update-post

{
  "post_id": "{_id}",
  "updates": {
    "status": "Ready_ToPublish",
    "reviewed_at": "{ISO_timestamp}",
    "review_decision": "approved"

On success: "Post approved! n8n {scheduled_date} ko auto-publish karega." Increment approved_count.

Decision 2: Edit (Minor)

Ask user: "Kya change karna hai? Content paste karo ya specific line batao."

Proceed to C.3 (Apply Minor Edits) with the current post and user's edit instructions.

Decision 3: Reschedule

Ask user for new date. Parse and convert to ISO format. Check for conflicts via sma-fetch-post.

Conflict check: If another post exists on the same date, inform user and re-ask. Max 1 post/day constraint enforced.

Moving to Next Post

  1. Increment current_post_index.
  2. If more posts remain → repeat C.2 for next post.
  3. If all posts reviewed → proceed to C.4 (Finalize Review).

Error Handling

Update fails: Retry once after 3 seconds. If still fails, mark post as "skipped" in local state. At C.4, remind about skipped posts.
Ambiguous user input (e.g., "theek hai"): Always disambiguate: "Confirm karo — approve matlab as-is publish, ya kuch edit karna hai?"

What NOT to Do

  • Do NOT auto-approve any post — every post needs explicit user confirmation
  • Do NOT apply edits without showing the user the result first (that's C.3's job)
  • Do NOT drop a post without double-confirmation from the user
  • Do NOT allow scheduling on a date that already has a post (1 post/day max)
  • Do NOT show draft_content — always show formatted_content
  • Do NOT proceed past a post without a clear decision
  • Do NOT make up or modify content on your own

Step C.3 — Apply Minor Edits

Agent: Pixel (flex-crafter)
Trigger: User chose "Edit" in C.2 for the current post.

What You Do

Take the user's edit instructions, apply them to the formatted_content, re-validate against formatting rules, show the updated preview, and loop until the user approves the edited version.

Execution Flow

1. Understand the Edit Request

Common edit types: typo fix, word swap, line rewrite, add/remove emoji, hashtag change, shorten. If unclear, ask: "Exactly kya change karna hai? Line number ya specific text batao."

2. Apply Edits to formatted_content

Make requested changes while maintaining all existing formatting:

  • Preserve staircase formatting / line breaks
  • Preserve UPPERCASE headers
  • Keep emoji count ≤ 3
  • Keep character count within 800–1600 range
  • Preserve bullet formatting (" - ") and flow formatting ("A —> B —> C")

3. Re-validate Formatting Rules

RuleCheck
Character count800–1600 ASCII chars
Emoji count≤ 3
No bold/italic/underlinePlain text only
Line blocksMax 3 lines per block
Hashtags3–6 at end
FK readabilityGrade 7 target
If any rule violated by the edit, inform user and help fix the violation before proceeding.

4. Show Updated Preview

Display the edited content in the same format as C.2 with an EDITED PREVIEW label, updated character count, and summary of changes. Ask: "Ye theek hai? (approve / aur edit / revert)"

5. User Decision on Edited Version

  • Approve: Save via sma-update-post with updated formatted_content, status Ready_ToPublish, review_decision: "edited_and_approved", and edit_summary. Increment edited_count.
  • "Aur edit": Ask for new edit instructions. Loop back. No limit on edit rounds.
  • "Revert": Restore original formatted_content. Return to C.2 decision prompt.

Error Handling

Save fails after edit approval: Retry once. If still fails, keep edited content in working memory (do NOT discard). Suggest user copy to clipboard as safety net.
Major edit detected: If edit would require major structural changes, suggest sending back to B-ContentDrafting instead.

Minor vs Major guideline:

  • Minor: Typos, word swaps, line tweaks, emoji changes, hashtag changes, shortening/lengthening within limits
  • Major: Changing the hook entirely, rewriting narrative structure, changing content format, changing topic angle

What NOT to Do

  • Do NOT save edits without showing the user the updated preview first
  • Do NOT apply edits that violate formatting rules without flagging it
  • Do NOT lose the original formatted_content — always keep it available for revert
  • Do NOT make additional "improvement" edits beyond what the user asked for
  • Do NOT change draft_content — only formatted_content is edited here
  • Do NOT auto-approve after editing — user MUST explicitly confirm

Error Handling Guide

Failure modes, race conditions, and recovery strategies for the Content Review workflow (C.1–C.4). The review workflow is the last human checkpoint before auto-publication.

1. Webhook Failures Mid-Review

1.1 sma-fetch-post Fails at C.1

Scenario: Network error or non-200 response when fetching Previewed posts.

Impact: Workflow cannot start — no posts to review.

Handling: Retry once after 5 seconds. If retry fails, surface the n8n workflow name: SMA/Data/Read/FetchPost. Do NOT proceed to C.2. Do NOT fabricate or cache stale post data.
1.2 sma-update-post Fails During C.2 Decision

Scenario: User approves/drops/reschedules a post, but the save webhook fails.

Impact: Decision made but not persisted — post remains Previewed in MongoDB.

Handling: Retry once after 3 seconds. If retry fails: add post to skipped_posts[] with the intended decision payload. Inform user. Do NOT discard the user's decision. At C.4, retry all skipped posts before presenting the summary. Never silently swallow a failed update.
1.3 sma-update-post Fails After Edit Approval (C.3)

Scenario: User edited content, approved the edit, but the save fails.

Impact: Edited content exists only in agent memory — will be lost if session ends.

Handling: Retry once. If retry fails: keep edited content in working memory (do NOT discard). Suggest user copy edited content to clipboard. Add to skipped_posts[] for C.4 retry. Do NOT revert to original content — the user's edits are the source of truth.
1.4 Webhook Timeout (Slow Response)

Scenario: n8n responds but takes >30 seconds.

Handling: Wait up to 60 seconds before treating as failure. If timeout occurs, check post status before retrying (fetch the post first to see if the update actually applied). If status already changed → update succeeded despite timeout. Do NOT re-send.

2. Conflicting Edits

2.1 Two Sessions Reviewing the Same Post

Scenario: User opens two review sessions. Both fetch the same Previewed post.

Prevention: The workflow is designed as a single-user interactive session. No multi-user concurrency in v1.

Detection: If a post's status has changed between fetch (C.1) and decision (C.2), warn: "Post '{topic}' ka status change ho chuka hai. Kisi aur ne already review kar liya. Skip karna padega."

Recovery: Skip the post. Do NOT overwrite a decision made by another session.

2.2 External Status Change During Review

Handling: Before applying any decision in C.2, optionally re-fetch the post's current status. Decision matrix by current status:

  • Published → Too late. Inform user. Cannot undo.
  • Cancelled → Someone else dropped it. Skip.
  • Ready_ToPublish → Already approved elsewhere. Skip or allow re-decision.
  • Drafting / Scheduled_NoDraft → Sent back. Skip.
Long sessions (>10 minutes) should trigger a staleness warning.

3. Status Race Conditions

3.1 Approve → Auto-Publish Race

Scenario: User approves a post. n8n's D-ContentPublishing picks it up and publishes it before the review session ends.

At C.4, if user requests undo: re-fetch status. If Published → cannot undo. If Ready_ToPublish → safe to revert to Previewed.
3.2 Reschedule → Date Conflict Race (TOCTOU)

Scenario: User reschedules to March 20. Between conflict check and update, another post gets scheduled for March 20.

Mitigation: D-ContentPublishing should also enforce 1 post/day at publish time (defense in depth). If duplicate detected downstream, D-ContentPublishing holds the second post and alerts user.

3.3 Drop → Re-Ideate Race

No conflict — the slot is legitimately free. The Cancelled post stays archived, and the new post fills the slot. This is expected behavior, not an error.

3.4 Send-Back → Re-Fetch Race

Extremely unlikely within a single session. If the re-formatted post appears on re-fetch, treat it as a fresh review item and inform user it was sent back and has been re-drafted.

4. Empty Queue Handling

4.1 Zero Posts at C.1

Do NOT proceed to C.2. Display message explaining no posts available. Offer alternatives. Exit gracefully — do NOT loop or poll.

4.2 Queue Empties Mid-Review

Agent works from its local array, not live queries. At decision time, if webhook rejects an update because status is wrong, handle per section 2.2.

4.3 All Posts Skipped Due to Failures
At C.4, retry ALL skipped posts. If all retries fail: present summary showing all as "Failed (needs manual fix)". Provide all post_id values. Suggest checking n8n health. Do NOT claim the review is "complete".

5. Undo After Auto-Publish Started

5.1 Undo Request During C.4 Summary

Re-fetch the post by _id to check current status.

Current StatusCan Undo?Action
Ready_ToPublishYesSet status back to Previewed
PublishedNoInform user: already live on LinkedIn, cannot retract
CancelledYesSet status back to Previewed (un-drop)
Scheduled_NoDraftPartiallyCan set back to Previewed if content still exists
5.2 Undo Request After Session Ends
  • Ready_ToPublish → start a new review session; can request manual status revert.
  • Published → cannot undo. LinkedIn does not support un-publishing via API.
  • Cancelled → can restore by manually updating status to Previewed.
5.3 Partial Publish (n8n Picks Up Mid-Batch)

Re-fetch all posts. Revert those still Ready_ToPublish. Inform user about already-published ones (irreversible). Log the partial undo in session summary.

6. Data Integrity Safeguards

6.1 Missing formatted_content

Do NOT present this post for review. Inform user: "Post '{topic}' mein formatted content nahi hai. F-ContentFormatting dobara run karo." Skip the post.

6.2 Stale scheduled_date (Past Date)
Flag at C.1: "Post '{topic}' ki date beet chuki hai ({past_date}). Reschedule ya drop karo." Present it first (most urgent). Do NOT auto-approve.
6.3 Counter Mismatch at C.4

If approved + edited + rescheduled + dropped + sent_back + skipped != total_posts: log a warning. Present whatever data is available — do not block finalization. Flag the mismatch for debugging.

7. Session-Level Failures

7.1 Agent Context Lost (Conversation Interrupted)

Use step-01b-resume-if-interrupted.md to recover. Re-fetch Previewed posts — already-decided posts will have changed status. Previously applied decisions are safe (persisted to MongoDB). Unsaved decisions in skipped_posts[] are lost.

7.2 Very Long Session (Context Window Pressure)

Decisions are persisted to MongoDB as they happen. Session counters should be maintained as compact state. At C.4, if counter data seems incomplete, re-fetch all posts and reconstruct from current statuses.
