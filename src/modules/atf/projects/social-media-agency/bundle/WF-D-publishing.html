Workflow D — Content Publishing

Steps: 6 core (01, 01b, D1, D2, D3, D4) + checklist, template, validation, edit, error-handling, test-plan

Status: Active | Code: D | Scope: LinkedIn only (v1) — Max 1 post/day

Goal: Take posts that have passed review (status = Ready_ToPublish), publish them to LinkedIn with safety guardrails (duplicate guard, random delay, one-shot rule), update their status to Published, and notify the team via Telegram.

Workflow Overview

System: This is a BMAD workflow — semi-automated. The agent executes each step, but the user confirms before the actual LinkedIn publish. ALL data reads and writes go through n8n webhooks. The agent has ZERO direct DB/API access.

Execution Instructions

This workflow handles the final mile — getting approved posts onto LinkedIn. By the time a post reaches this workflow, it has already been through Ideation (A), Drafting (B), Formatting (F), and Review (C). The post status is Ready_ToPublish. Your job: publish it safely, update the records, and notify the team.

Pre-requisites

  1. Post status is Ready_ToPublish — if it's anything else, do NOT publish. Send it back to the appropriate workflow.
  2. The post came through C (Content Review) — it must have been explicitly approved.
  3. No post has already been published today — max 1 post/day rule (v1).
  4. You have ZERO direct DB/API access — every read and write goes through n8n webhooks.

Error Handling Summary

StepErrorAction
D.1Webhook failsRetry once, then ask user to check n8n
D.1No posts foundInform user, exit gracefully
D.2Duplicate URN foundSKIP post, inform user
D.2LinkedIn API errorDo NOT retry. Mark Publish_Failed. Inform user.
D.2TimeoutTreat as failure. One-shot rule applies.
D.3Update webhook failsWarn user. Post is still live. Do not rollback.
D.4Telegram failsLog warning. Workflow still succeeds.

What NOT to Do

  • Do NOT retry a failed LinkedIn publish — one-shot rule is absolute.
  • Do NOT publish a post that doesn't have Ready_ToPublish status.
  • Do NOT publish more than 1 post per day.
  • Do NOT auto-select which post to publish — always let the user choose.
  • Do NOT fabricate a linkedin_post_urn if the API didn't return one.
  • Do NOT attempt to delete or rollback a LinkedIn post if a later step fails.
  • Do NOT skip the duplicate guard check.
  • Do NOT skip the random delay without user explicitly requesting it.
  • Do NOT access any database or API directly — everything goes through webhooks.
  • Do NOT proceed to D.3 if D.2 failed — the post isn't published.

Step 01 — Load Session Context

Agent: Content Publisher | Trigger: User initiates the content-publishing workflow (e.g., "Publish karo", "Post daal do", "Let's publish").

What You Do

Before executing any publish steps, load the workflow context and check for any in-progress sessions.

Actions

  1. Load workflow config — Read workflow.yaml to confirm you're in the content-publishing (D) workflow.
  2. Check for in-progress sessions — Look for any publish session that was started but not completed:
    • A post was fetched (D.1 done) but not yet published (D.2 pending)
    • A post was published (D.2 done) but status not updated (D.3 pending)
    • If an in-progress session is found, proceed to step-01b-resume-if-interrupted.md
  3. Confirm environment — Verify:
    • The base webhook URL is reachable: https://n8n.linkright.in/webhook/
    • No other publish workflow is currently running
  4. Set session variables:
    • workflow_code: D
    • workflow_name: content-publishing
    • session_start: current ISO 8601 timestamp
    • posts_published_today: count of posts already published today

After Loading

If no in-progress session exists, proceed to D.1. If an in-progress session is found, proceed to Step 01b.

Do NOT skip session context loading — it prevents duplicate publishes. Do NOT proceed if posts_published_today >= 1 — max 1 post/day rule.

Step 01b — Resume If Interrupted

Agent: Content Publisher | Trigger: Step 01 detected an in-progress publish session that was interrupted.

What You Do

Recover from an interrupted publish session. Determine where the workflow stopped and resume from the last known good state.

Recovery Logic

Case 1: Post fetched, not yet published (D.1 done, D.2 pending)

The post was selected for publishing but the publish call was never made (or outcome unknown).

Action: Check if the post has a linkedin_post_urn.

  • If URN exists → post was actually published. Skip to D.3 (update status).
  • If no URN → post was not published. Resume from D.2 (publish).

Case 2: Post published, status not updated (D.2 done, D.3 pending)

LinkedIn publish succeeded (URN captured) but the status update failed or was never made.

Action: Resume from D.3. Use the captured linkedin_post_urn and published_at from the session.

Case 3: Status updated, Telegram not sent (D.3 done, D.4 pending)

Everything succeeded except the Telegram notification.

Action: Resume from D.4. Send the notification.

Case 4: Unknown state

Cannot determine where the workflow stopped.

Action: Fetch the post by ID and check its current status and fields:

  • Ready_ToPublish + no URN → start from D.1
  • Published + URN + published_at → workflow is complete, just send Telegram if missing
  • Publish_Failed → inform user, do NOT retry (one-shot rule)
Do NOT re-publish a post that already has a linkedin_post_urn — duplicate guard applies. Do NOT retry a Publish_Failed post — one-shot rule is absolute. Do NOT guess the state — always verify by checking the post record.

Step D.2 — Publish to LinkedIn

Agent: Content Publisher (Relay) | Trigger: User confirmed a post selection in D.1.

This is the most critical step in the entire SMA pipeline. A bad publish cannot be undone programmatically. Follow every guardrail exactly — no exceptions.

Guardrail 1: Duplicate Guard (THREE checks)

Check 1 — Post Status Not Already Published

Verify the selected post's status field is still Ready_ToPublish. If status is Published, Publish_Failed, or anything else: STOP. Exit the workflow.

Check 2 — No Post Published Today

Fetch today's published posts to verify no post has already been published today:

{
  "status": "Published",
  "published_date": "2026-03-14"
}

If response returns any post with published_at matching today: STOP. User can explicitly override by saying "publish anyway" — log the override.

Check 3 — LinkedIn URN Not Already Set

Check the selected post's linkedin_post_urn field. If it already has a value: STOP. Ask user to select a different post or exit.

Guardrail 2: Random Delay

Generate a random delay to make posting times appear natural and non-robotic.

delay_minutes = Math.floor(Math.random() * 61)  // 0-60 inclusive

If the user says "publish now" or similar, skip the delay. Otherwise, wait the full delay period. During the wait, do NOT make any other webhook calls.

Action: Call n8n Webhook

POST https://n8n.linkright.in/webhook/sma-publish-linkedin

{
  "post_id": "<post_id from selected_post>",
  "content": "<full post content -- exactly as approved in Review (C), no modifications>",
  "hashtags": ["#DevTools", "#DX", "#SaaS"],
  "title": "<post title>",
  "topic": "<post topic>",
  "scheduled_date": "<scheduled_date from post>"
}

CRITICAL: Send the content exactly as it was approved in Review (C). Do NOT reformat, trim, or modify any part of the content or hashtags.

Expected Success Response (HTTP 200)

{
  "success": true,
  "linkedin_post_urn": "urn:li:share:7307123456789012345",
  "linkedin_post_url": "https://www.linkedin.com/feed/update/urn:li:share:7307123456789012345",
  "published_at": "2026-03-14T10:30:00Z"
}

One-Shot Rule — ABSOLUTE, NON-NEGOTIABLE

If the publish webhook returns ANY error (HTTP non-200, network timeout, connection refused, success: false, missing linkedin_post_urn, any exception):
  1. Do NOT Retry. Not once. Not ever. Not even if the user asks.
  2. Capture the Error — HTTP status code, error message, timestamp.
  3. Mark Post as Publish_Failed via sma-update-post.
  4. Inform the User with exact error details.
  5. Exit. Do NOT proceed to D.3 or D.4.

On Success

Store in working memory: linkedin_post_urn, linkedin_post_url, published_at, delay_applied. Tell the user the post is live. Proceed to D.3.

Output for Next Step

Pass to D.3: post_id, title, linkedin_post_urn, linkedin_post_url, published_at, delay_applied.

Step D.3 — Update Post Status

Agent: Content Publisher (Relay) | Trigger: D.2 completed successfully — post is live on LinkedIn.

What You Do

Update the post record in MongoDB to reflect its published state. This ensures the rest of the pipeline (E-Analytics, dashboards, duplicate guards) knows the post is live. Four fields are updated: status, published_at, linkedin_post_urn, and linkedin_post_url.

Action: Call n8n Webhook

POST https://n8n.linkright.in/webhook/sma-update-post

{
  "post_id": "<post_id from D.2>",
  "status": "Published",
  "published_at": "<ISO 8601 timestamp from D.2>",
  "linkedin_post_urn": "<URN from D.2>",
  "linkedin_post_url": "<URL from D.2>"
}

Expected Success Response (HTTP 200)

{
  "success": true,
  "updated": true
}

After the Call

If update succeeds: Confirm to the user. Proceed to D.4.

If update fails: This is a non-critical failure. The post is already live on LinkedIn — the publish cannot be undone. Warn the user, provide the linkedin_post_urn for manual recovery, retry once after 5 seconds. If retry also fails, log the error and proceed to D.4 anyway.

Verification (Optional)

After a successful update, optionally verify by re-fetching the post and confirming that status, linkedin_post_urn, linkedin_post_url, and published_at are all set correctly.

Output for Next Step

Pass to D.4: post_id, title, linkedin_post_urn, linkedin_post_url, published_at, delay_applied, update_status ("success" or "failed").

Do NOT rollback or delete the LinkedIn post if the update fails. Do NOT skip this step — downstream workflows depend on it. Do NOT block the entire workflow if the update fails — proceed to D.4.

D.1 — Fetch Ready Posts Errors

ERR-D1-01: Webhook Network Failure

Detection: HTTP connection error, DNS resolution failure, or connection refused when calling sma-fetch-post.

Response: Wait 5 seconds, retry once.

Recovery: If retry succeeds, continue normally. If retry fails, inform user, exit workflow.

Severity: FATAL

ERR-D1-02: Webhook Non-200 Response

Detection: HTTP status code is not 200 (e.g., 502 Bad Gateway, 500 Internal Server Error).

Response: Same as ERR-D1-01 — retry once after 5 seconds.

Severity: FATAL

ERR-D1-03: Empty Post List

Detection: Webhook returns HTTP 200 but posts array is empty.

Response: Inform user. Exit workflow gracefully. No retry needed — this is a valid state.

Severity: N/A — expected state, not an error.

ERR-D1-04: Malformed Response

Detection: Response is not valid JSON, or posts field is missing/not an array.

Response: Treat as webhook failure (ERR-D1-01 path). Retry once.

Severity: FATAL

D.2 — Publish to LinkedIn Errors

ERR-D2-01: LinkedIn API 401 Unauthorized

Detection: Publish webhook returns HTTP 401.

Response: Do NOT retry (one-shot rule). Mark post as Publish_Failed. Capture error.

Root Cause Checklist: LinkedIn OAuth token expired (60-day cycle), n8n LinkedIn credential node misconfigured, LinkedIn app permissions revoked.

Severity: FATAL — requires credential fix.

ERR-D2-02: LinkedIn API 403 Forbidden

Detection: Publish webhook returns HTTP 403.

Response: Do NOT retry. Mark Publish_Failed.

Root Cause Checklist: Missing w_member_social permission, account restricted by LinkedIn, posting to a page without admin rights.

Severity: FATAL

ERR-D2-03: LinkedIn API 429 Rate Limited

Detection: Publish webhook returns HTTP 429.

Response: Do NOT retry (one-shot rule — retrying risks duplicate posts). Mark Publish_Failed.

Root Cause Checklist: LinkedIn API daily rate limit hit, multiple tools posting from same account, rapid successive publish attempts.

Severity: FATAL — transient, resolves after rate limit window resets.

ERR-D2-04: LinkedIn API 500 Internal Server Error

Detection: Publish webhook returns HTTP 500, 502, 503, or 504.

Response: Do NOT retry. Mark Publish_Failed. Log full error response.

Important: On 5xx errors, it is ambiguous whether the post was actually created on LinkedIn. Before re-queuing: check the LinkedIn profile manually. If post IS live, manually set status to Published. If not live, safe to re-queue.

Severity: FATAL — may require manual verification.

ERR-D2-05: Network Timeout

Detection: Webhook call exceeds timeout threshold (30s) without response.

Response: Do NOT retry. Mark Publish_Failed.

CRITICAL WARNING: Timeouts are the most dangerous error because the post may have been successfully created on LinkedIn before the timeout occurred. ALWAYS verify manually before re-queuing.

Severity: FATAL — ambiguous state.

ERR-D2-06: Duplicate Publish Prevention — URN Already Exists

Detection: Selected post has a non-null, non-empty linkedin_post_urn field.

Response: STOP immediately. Do NOT call the publish webhook.

Recovery: Ask user to select a different post or exit workflow.

Severity: Prevented error — guardrail working correctly.

ERR-D2-07: Duplicate Publish Prevention — Already Published Today

Detection: Today's published posts returns results with published_at matching today (UTC).

Response: STOP. Inform user of 1/day limit. User can explicitly override — log the override.

Severity: Prevented error — guardrail working correctly.

ERR-D2-08: Response Missing linkedin_post_urn

Detection: Webhook returns HTTP 200 and success: true, but linkedin_post_urn is null, empty, or missing.

Response: Treat as publish failure (one-shot rule). Mark Publish_Failed.

Severity: FATAL — ambiguous state.

ERR-D2-09: success: false in Response Body

Detection: Webhook returns HTTP 200 but response body contains "success": false.

Response: Do NOT retry. Mark Publish_Failed. Extract and log error message.

Severity: FATAL

D.3 — Status Update Errors

ERR-D3-01: MongoDB Write Failure (via n8n)

Detection: Update webhook returns non-200, timeout, or success: false.

Response: Warn user (post IS live on LinkedIn, but DB record is stale). Retry once after 5 seconds.

Recovery: If retry succeeds, continue to D.4. If retry fails, proceed to D.4 anyway with warning in Telegram notification.

Impact if not fixed: E-Analytics workflow won't pick up the post, duplicate guard may fail, post may appear as Ready_ToPublish in future D.1 fetch.

Manual Fix:

db.linkedin_posts.updateOne(
  { _id: ObjectId("<post_id>") },
  {
    $set: {
      status: "Published",

Error Recovery Procedures

Recovering from Publish_Failed
  1. Investigate the error — check publish_error and failed_at fields on the post record
  2. Check LinkedIn manually — verify the post did NOT appear on the LinkedIn profile (especially for timeout/5xx errors)
  3. Fix root cause — resolve the underlying issue (token refresh, rate limit wait, etc.)
  4. Re-queue the post — set status back to Ready_ToPublish, clear publish_error and failed_at
  5. Re-run the D workflow — start from D.1
NEVER re-queue without manual LinkedIn verification — this prevents duplicate posts.
Recovering from D.3 Failure (Post Live, DB Stale)
  1. Immediately save the URN — copy from agent conversation or Telegram notification
  2. Fix n8n — check SMA/Data/Write/UpdatePost workflow is active
  3. Manual update — use MongoDB shell or re-trigger the update webhook
  4. Verify — fetch the post and confirm all four fields are set correctly
Recovering from Interrupted Workflow

D.2 (failure)Post marked Publish_FailedFollow Publish_Failed recovery
D.3Post live, DB may/may not be updatedVerify DB state, run D.4 if not sent
